## 🎯 О работе

Массив — непрерывный блок памяти, доступ к элементу по индексу за **O(1)**.
В этой работе он собран вручную: каждая ячейка — указатель на объект Python (`PyObject`),
память выделяется через `ctypes`, а всё остальное (рост, сжатие, сдвиги, поиск) написано явно.

Цель — не «получить работающий массив», а **увидеть, почему** `append` быстрый,
`insert(0, x)` медленный, и чем за это платит память.

## 🧩 Что реализовано

<details open>
<summary><b>StaticArray</b> — статический массив фиксированной ёмкости</summary>

<br>

```python
from static_array import StaticArray

arr = StaticArray(5)            # выделяем память под 5 элементов
for i in range(5):
    arr.append(i * 10)          # [0, 10, 20, 30, 40]

arr.get(2)                      # 20        — O(1)
arr.set(2, 999)                 # [0, 10, 999, 30, 40]
len(arr)                        # 5
arr.append(100)                 # OverflowError: Array is full
arr.get(10)                     # IndexError: Index out of bounds
```

| Метод | Сложность | Описание |
|---|:---:|---|
| `get(index)` | O(1) | Чтение по индексу с проверкой границ |
| `set(index, value)` | O(1) | Запись по индексу с проверкой границ |
| `append(value)` | O(1) | Добавление в конец, пока есть место |
| `__len__()` | O(1) | Текущее количество элементов |
| `__str__()` | O(n) | Представление вида `[1, 2, 3]` |

</details>

<details open>
<summary><b>DynamicArray</b> — динамический массив с ростом и сжатием</summary>

<br>

```python
from dynamic_array import DynamicArray

da = DynamicArray()             # capacity = 1
for i in range(100):
    da.append(i)                # ёмкость удваивается: 1 → 2 → 4 → ... → 128

da.get(50)                      # 50
da.insert(10, 999)              # сдвиг вправо, вставка
da.remove(10)                   # сдвиг влево, при size == capacity/4 — сжатие
da.find(50)                     # 50   — линейный поиск
da.binary_search(50)            # 50   — бинарный (массив должен быть отсортирован)
```

| Метод | Сложность | Что происходит внутри |
|---|:---:|---|
| `append(value)` | O(1) амортиз. | При заполнении — `_resize(2 × capacity)` |
| `get(index)` | O(1) | Прямое обращение к памяти |
| `insert(index, value)` | O(n) | Сдвиг элементов **справа налево** |
| `remove(index)` | O(n) | Сдвиг **слева направо** + возможное сжатие |
| `find(value)` | O(n) | Линейный проход, возвращает индекс или `None` |
| `binary_search(value)` | O(log n) | Деление отрезка пополам, требует сортировки |

</details>

<details>
<summary><b>DynamicArrayGold</b> — массив с настраиваемым коэффициентом роста</summary>

<br>

```python
from dynamic_array_gold import DynamicArrayGold, compare_growth_factors

arr = DynamicArrayGold(1.5)     # рост в 1.5 раза вместо 2
for i in range(10):
    arr.append(i)
print(len(arr), arr._capacity)  # 10 11

compare_growth_factors()        # таблица + график сравнения 2.0 и 1.5
```

Новая ёмкость считается как `int(capacity * growth_factor) + 1`.
Слагаемое `+ 1` обязательно: при `capacity = 1` и `factor = 1.5` результат `int(1.5) = 1`,
массив бы не вырос и `append` зациклился.

</details>

## 📐 Вычислительная сложность

| Операция | Static Array | Dynamic Array | list (Python) \*\* |
|---|:---:|:---:|:---:|
| Доступ по индексу | `O(1)` | `O(1)` | `O(1)` |
| Вставка в конец | `O(1)` \* | `O(1)` амортиз. | `O(1)` амортиз. |
| Вставка в начало | `O(n)` | `O(n)` | `O(n)` |
| Вставка в середину | `O(n)` | `O(n)` | `O(n)` |
| Удаление из конца | `O(1)` \* | `O(1)` | `O(1)` |
| Удаление из начала | `O(n)` | `O(n)` | `O(n)` |
| Удаление из середины | `O(n)` | `O(n)` | `O(n)` |
| Поиск линейный | `O(n)` | `O(n)` | `O(n)` |
| Поиск бинарный | `O(log n)` | `O(log n)` | `O(log n)` |

<sub>\* Для статического массива — только при наличии свободного места, иначе `OverflowError`.</sub>
<sub>\*\* Встроенные контейнеры Python используются **только для сравнения** — структуры данных реализованы самостоятельно, с нуля, через классы.</sub>

## 📈 Результаты замеров

Замеры: `time.perf_counter()`, каждое измерение повторено 3 раза, взято среднее.
`n = 10 000 / 100 000 / 1 000 000`.

<div align="center">

![append и insert](results/append_insert.png)

</div>

**`append` — весь цикл из n добавлений**

| n | DynamicArray | list | Отношение |
|---:|---:|---:|---:|
| 10 000 | 0.0035 с | 0.00012 с | ×29 |
| 100 000 | 0.0333 с | 0.00114 с | ×29 |
| 1 000 000 | 0.3948 с | 0.01317 с | ×30 |

**`insert(0, value)` — одна вставка в начало**

| n | DynamicArray | list | Отношение |
|---:|---:|---:|---:|
| 10 000 | 0.0013 с | 0.0000031 с | ×429 |
| 100 000 | 0.0132 с | 0.0000292 с | ×454 |
| 1 000 000 | 0.2244 с | 0.0016015 с | ×140 |

> **Главный вывод.** Время растёт линейно от `n` в обоих случаях, но смысл разный:
> у `append` линейно растёт **суммарное** время цикла → на одну операцию приходится
> константа (амортизированная `O(1)`). У `insert(0, x)` линейно растёт время **одной**
> операции → это честная `O(n)`. Собственная реализация медленнее `list` в десятки раз,
> но это разница в **константе**, а не в асимптотике: прямые на логарифмическом графике
> параллельны, а `list` просто выполняет сдвиг в C-коде через `memmove`.

### Золото: 2.0 против 1.5

<div align="center">

![Коэффициенты роста](results/growth_factors.png)

</div>

| n | factor 2.0 | factor 1.5 | Разница |
|---:|---:|---:|---:|
| 1 000 | 0.000313 с | 0.000472 с | −34 % |
| 10 000 | 0.003581 с | 0.004528 с | −21 % |
| 100 000 | 0.033235 с | 0.052890 с | −37 % |

Коэффициент **2.0 быстрее на 15–37 %**: расширений меньше (≈ 17 против ≈ 29 на 100 000
добавлений), а каждое расширение копирует весь массив. Плата — память: при 2.0 до половины
ёмкости может простаивать, при 1.5 — около 30 %. Классический компромисс
«скорость против памяти».

## 💡 Ключевые идеи

<details>
<summary><b>Почему <code>append</code> — амортизированная O(1), если внутри бывает копирование всего массива?</b></summary>

<br>

Ёмкость удваивается, поэтому расширения происходят всё реже. Суммарное количество
копирований за `n` добавлений:

```
1 + 2 + 4 + 8 + ... + n/2  ≈  n
```

То есть на одно добавление приходится примерно 2 операции — константа.
На миллион добавлений расширений всего ≈ log₂(1 000 000) ≈ 20.

</details>

<details>
<summary><b>Почему при <code>insert</code> сдвиг идёт справа налево, а при <code>remove</code> — слева направо?</b></summary>

<br>

Чтобы не затереть ещё не скопированные данные.

**insert:** массив `[A, B, C]`, вставляем `X` на позицию 1.

```
i = 3:  arr[3] = arr[2]   →  [A, B, C, C]
i = 2:  arr[2] = arr[1]   →  [A, B, B, C]
затем:  arr[1] = X        →  [A, X, B, C]
```

Если идти слева направо, `B` перезапишет `C` — и `C` будет потерян.

**remove:** массив `[A, B, C, D]`, удаляем индекс 1.

```
i = 1:  arr[1] = arr[2]   →  [A, C, C, D]
i = 2:  arr[2] = arr[3]   →  [A, C, D, D]
size -= 1                 →  [A, C, D]
```

Здесь, наоборот, справа налево потеряли бы данные.

</details>

<details>
<summary><b>Почему сжатие срабатывает при ¼ ёмкости, а не при ½?</b></summary>

<br>

Если сжимать при ½, то чередование «добавили элемент → расширение, удалили → сжатие»
заставит массив реаллоцироваться на каждой операции — это очень медленно.

Порог ¼ создаёт **гистерезис**: после сжатия до половины ёмкости остаётся запас
для новых добавлений, и «пиления» памяти на границе не происходит.

</details>

<details>
<summary><b>Линейный или бинарный поиск?</b></summary>

<br>

| | Линейный | Бинарный |
|---|---|---|
| Сложность | `O(n)` | `O(log n)` |
| Требования | нет | массив отсортирован |
| 1 млн элементов | ≈ 0.01 с | ≈ 0.00001 с |

Бинарный поиск на три порядка быстрее, но за сортировку тоже нужно платить —
он окупается, когда по одному отсортированному массиву ищут многократно.

</details>
